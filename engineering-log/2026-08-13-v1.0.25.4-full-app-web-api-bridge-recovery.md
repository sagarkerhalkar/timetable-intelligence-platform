## Root cause
The recovered frontend API client uses `NEXT_PUBLIC_API_URL=/backend` by default and server-side code uses `INTERNAL_API_URL` when available. The running web build had no reliable same-origin `/backend -> http://127.0.0.1:3550` route, while server rendering also lacked a guaranteed absolute internal API URL. As a result the browser received 404/fallback empty states even though FastAPI and the authoritative DB were healthy.

## Fix
v1.0.25.4 recovery adds:
1. `apps/web/app/backend/[...path]/route.ts` catch-all same-origin proxy to API 3550 for GET/POST/PUT/PATCH/DELETE/OPTIONS, including query strings and binary QR responses.
2. Web runtime contract:
   - `INTERNAL_API_URL=http://127.0.0.1:3550`
   - `NEXT_PUBLIC_API_URL=/backend`
3. Read-only DB/direct-API prechecks before any web change.
4. Backup of prior web proxy/env/.next only.
5. TypeScript and production Next.js build gates.
6. Direct production start on `0.0.0.0:3500`; automatic current-source dev fallback only if Windows refuses production start.
7. Acceptance through the exact browser path `http://127.0.0.1:3500/backend/...`, requiring sources, Today timetable and QR data to be visible.
8. Main-page checks for Today, Week, Sources, Content, Sheet Updates, Test Monitor and My QR Codes.

## Safety
