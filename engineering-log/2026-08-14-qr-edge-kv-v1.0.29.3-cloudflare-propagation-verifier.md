# 2026-08-14 — QR Edge KV v1.0.29.3 Cloudflare propagation verifier

## User-reported failure

Real Windows acceptance of v1.0.29.2 failed with:

`NOT ACCEPTED: q Worker v1.0.29.2 marker x-ntqr-fast=3 is missing.`

The automatic rollback attempt then raised an error. The failed-run KV namespace was preserved. The installer reported that the production DB was not migrated/deleted.

## Root cause found in installer

v1.0.29.2 called a generic `Wait-Http()` helper immediately after `wrangler deploy`. That helper returned on the first HTTP 200 from the workers.dev health URL. During Cloudflare Worker deployment propagation, an edge may temporarily still serve the previous deployed version. Therefore a valid old-version 200 could be interpreted as a failed new deployment.

The installer then checked the marker only once and started rollback instead of continuing to wait for the requested build/version.

A second deployment-safety gap was also found: the Wrangler config did not pin the intended Cloudflare account, so the build did not prove which account received the Worker/KV operations.

## v1.0.29.3 correction

- Pin Wrangler deployment to the intended Cloudflare account. The exact account identifier is intentionally omitted from this public engineering log.
- Verify `wrangler whoami` exposes the intended account before Worker/KV writes.
- Add Cloudflare Worker version-metadata binding `CF_VERSION_METADATA`.
- Add a build identifier exposed by the Worker health response.
- Change Worker marker to `x-ntqr-fast: 4`.
- Add `Wait-WorkerBuild` that polls up to 180 seconds for the exact build contract instead of accepting any 200 response.
- Ignore temporary old-version 200 responses during propagation.
- Require the health response to show the new build ID, KV binding, intended-account marker, and a valid Worker version ID.
- If Wrangler exposes `Current Version ID`, compare it with the version metadata returned by the live Worker.
- Make rollback use the pinned Wrangler config/account.
- Preserve the KV namespace on failed acceptance.
- No production DB schema migration/delete/replace is introduced.
- Web port 3500 remains untouched; protected dev port 3457 remains untouched.
