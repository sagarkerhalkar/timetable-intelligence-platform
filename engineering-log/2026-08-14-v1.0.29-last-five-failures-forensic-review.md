# 2026-08-14 — Forensic review of the last five QR Edge KV failures

## Scope

User stopped before applying v1.0.29.5 because the application is now perceived as misbehaving and requested a review before any further update.

This review covers the five Windows attempts immediately before v1.0.29.5:

1. `v1.0.29`
2. `v1.0.29.1`
3. `v1.0.29.2`
4. `v1.0.29.3`
5. `v1.0.29.4`

No new production update is authorized by this review. `v1.0.29.5` is **not accepted and should not be run until current runtime/Cloudflare state is inspected read-only**.

## Evidence reviewed

- User-posted Windows installer outputs from 2026-08-14.
- The locally generated ZIP source for v1.0.29 through v1.0.29.5.
- GitHub `nexttoppersqr` release-source already committed for the QR fast/edge work.

The production DB was repeatedly reported by the installers as not migrated/deleted. The user-posted failure snippets also show API source/runtime rollback attempts and, in some attempts, KV cleanup or preservation.

## Failure 1 — v1.0.29

### Observed failure

`NOT ACCEPTED: Core DB counts changed during API source/runtime switch. Refusing acceptance.`

### Code cause

The installer compared full live table counts before and after restarting API 3550 and required exact equality.

That is invalid for a live application because legitimate writes can occur while the installer is running, including QR scans, timetable/source sync, Sheet Updates, Test Monitor data, and other background activity.

### Classification

**False acceptance failure caused by an invalid safety invariant.**

The row-count change was not evidence of DB corruption.

## Failure 2 — v1.0.29.1

### Observed failure

`NOT ACCEPTED: API could not populate the Cloudflare QR edge route store within 45 seconds.`

### Code cause that is proven

The new DB guard was improved, but the installer still required a FastAPI daemon thread to push the full/delta QR route snapshot to:

`https://q.nexttoppers.workers.dev/__ntqr_admin/sync`

The API thread:

- read all QR routes from SQLite,
- ran every 1 second,
- used a local secret file,
- made an outbound HTTPS request to the public Worker,
- and the installer required `edge-sync-status.last_ok == true` before acceptance.

### What is not proven from the pasted snippet

The exact internal `last_error` generated by `_edge_post()` is not present in the user-posted excerpt, so the precise HTTP/TLS/secret/network exception cannot be stated as fact.

### Classification

**Fragile acceptance dependency.** The installer treated a secondary background push daemon as mandatory even though the objective was scan-path latency.

## Failure 3 — v1.0.29.2

### Observed failure

`NOT ACCEPTED: q Worker v1.0.29.2 marker x-ntqr-fast=3 is missing.`

### Code cause

After `wrangler deploy`, the installer used `Wait-Http()` which returned on the first acceptable HTTP response. It then immediately compared the Worker marker.

During Worker propagation, an edge can still temporarily serve the previous version. Therefore an HTTP 200 from the old Worker was enough to cause an immediate false failure instead of waiting for the specific newly deployed build.

v1.0.29.2 also introduced explicit route seeding, but still retained the same local FastAPI background-push acceptance gate afterward.

### Classification

**Deployment verification race / wrong readiness criterion.**

## Failure 4 — v1.0.29.3

### Observed failure

Cloudflare returned:

`A KV namespace with the title "nexttoppers_qr_edge" already exists.`

### Code cause

The installer tried to reuse the namespace first, but its parser assumed the namespace-list output contained a JSON array and looked primarily for `.title`.

With the actual Wrangler output format, the existing namespace ID was not recognized, so the installer incorrectly tried to create the same namespace again.

### Classification

**Non-idempotent Cloudflare resource discovery caused by brittle CLI-output parsing.**

## Failure 5 — v1.0.29.4

### Observed failure

`NOT ACCEPTED: API could not populate the Cloudflare QR edge route store within 20 seconds.`

### Important proven sequence from the code

Before reaching that failure, v1.0.29.4 had already required and passed these earlier gates in sequence:

1. exact Cloudflare account verification,
2. Worker deployment,
3. exact Worker build/version verification,
4. Worker admin status confirming the edge secret + KV binding,
5. explicit seeding of all current QR routes into KV,
6. API 3550 restart,
7. SQLite integrity / foreign-key / schema checks.

Only after those gates did it run:

`$sync = Wait-EdgeSync 20`

That second gate again required the local FastAPI background thread to push to the Worker and set `last_ok=true`.

Therefore the installer rolled back **after the explicit KV seed had already succeeded**, because it unnecessarily required a second synchronization mechanism.

### Classification

**Architectural acceptance error: duplicate sync mechanisms, with the less reliable mechanism allowed to invalidate the already-successful primary seed.**

## Systemic problem across the five attempts

The main problem was not five unrelated Cloudflare defects. The development process kept adding a new fix on top of a multi-system installer without first isolating the failing subsystem.

The packages combined too many stateful operations in one acceptance transaction:

- local API source changes,
- API process restart,
- SQLite safety checks,
- Worker deployment,
- Worker version verification,
- Worker secret changes,
- KV namespace creation/binding,
- KV route seed,
- background synchronization,
- scan timing verification,
- Worker rollback,
- local source rollback,
- KV delete/preserve decisions.

A failure in any late check triggered rollback even when earlier critical-path work was already successful.

## Why the app may now appear to misbehave

This is a real risk and must be inspected before another update.

The rollback is not a true cross-system transaction.

The Windows rollback restores local source/runtime, but Cloudflare itself warns that Worker rollback does not roll back bound resources such as KV and other bindings. Across the failed attempts, Cloudflare-side state may therefore persist even after Worker code is rolled back, including:

- the `nexttoppers_qr_edge` namespace,
- KV content seeded by an attempted release,
- Worker secret/binding state,
- version/deployment history.

This can leave a mixed state: previous local API source + previous Worker code + newer Cloudflare resource/binding state.

This is a **possible cause of the current misbehaviour**, but current live state must be checked read-only before calling it confirmed.

## Additional design issue

The FastAPI QR sync loop in v1.0.29–v1.0.29.4 reads the QR snapshot every second and is wired into startup/health/resolve/confirm paths through `_ensure_edge_sync_thread()`.

Even though it only sends deltas after the first successful snapshot, this background mechanism increases coupling between the local app and Cloudflare and should not be used as an installer acceptance prerequisite.

## Decision / freeze

- Do **not** run v1.0.29.5 yet.
- Do **not** deploy another QR patch yet.
- Do **not** delete the existing KV namespace manually.
- Do **not** regenerate old QRs.
- Do **not** modify the production DB.
- Protect dev port 3457.

Next engineering action must be **read-only current-state inspection** of:

1. API 3550 health and actual source/version currently running,
2. web 3500 health,
3. current DB path, integrity, schema hash and key counts,
4. current Worker `q` version/build/health response,
5. current Worker bindings/secrets presence (names only, no secret values),
6. existing KV namespace ID and key count,
7. whether a sample QR is served from KV, origin, or the older Worker path,
8. current scan latency broken down by Worker/KV vs destination,
9. no changes to 3457.

Only after that state is known should a single cleanup/recovery plan be built.
