# 2026-08-14 - NextToppers QR v1.0.29 Edge KV latency fix

## User-visible failure

After v1.0.28.1 was deployed and the new `q.nexttoppers.workers.dev` QR hostname was working, a real phone scan still required about **5-8 seconds** to reach the final destination.

Result: **FAIL / performance not accepted**.

## Root cause

The v1.0.28 Worker removed the full Next.js scan page, but the normal scan request still synchronously executed:

`q.nexttoppers.workers.dev -> fetch https://nexttoppers.sagarkerhalkar.com/backend/api/v1/qr-fast/<slug>/resolve -> Cloudflare Tunnel -> local FastAPI/SQLite -> Worker -> browser -> destination`

The Worker source explicitly used `cache: "no-store"` for that resolver, so every scan paid the origin/Tunnel round trip. The scan HTML also retained a configured redirect delay (historically defaulting to about 650 ms). The v1.0.28 Worker configuration also enabled Smart Placement because it still depended on the backend.

This means the earlier optimization removed the heavy web bundle but did **not** remove the slow network dependency from the critical path.

## v1.0.29 corrective architecture

Normal route lookup moves to Cloudflare Workers KV:

`phone -> closest q Worker -> QR_EDGE KV -> tiny browser-confirmed analytics page -> destination`

The local API/Tunnel is no longer synchronously queried during a normal KV-hit scan.

The API-side `qr_fast.py` now maintains the edge route map. In production it checks `qr_codes` for changes every second and sends only changed/deleted route records to a protected Worker admin sync endpoint. The Worker stores those route records in `QR_EDGE` KV. The sync secret is generated only on the Windows server and configured as a Cloudflare Worker secret; it is not committed to GitHub.

On a rare KV miss, the Worker can fall back to the existing resolver and warm KV. Existing QR IDs, slugs, destinations, analytics history, active/inactive behavior and the production SQLite schema remain unchanged.

## Performance changes

- Normal scan route lookup: Workers KV instead of synchronous local API/Tunnel.
- Smart Placement removed from the `q` Worker configuration so the Worker uses Cloudflare's default execution nearest the incoming request; backend placement is no longer required for the normal route lookup.
- Anonymous tracked QR intentional redirect delay capped at 120 ms.
- Browser telemetry is still sent with `sendBeacon` / keepalive.
- Analytics persistence to the local API remains asynchronous through Worker `ctx.waitUntil()` and does not block the user's redirect.
- Worker response exposes `x-ntqr-fast: 2` and `x-ntqr-source: kv` for acceptance evidence.

## Safety

- No production database migration, replacement or deletion.
- API source is backed up before runtime switch.
- Full existing backend pytest suite runs against an isolated temporary database before runtime switch.
- Worker JavaScript syntax is checked before deployment.
- Only API port 3550 is restarted after validation.
- Web 3500 is not stopped.
- Protected dev port 3457 is not touched.
- Cloudflare Worker rollback and API source rollback are attempted if post-deployment acceptance fails.
- No Cloudflare secret is stored in this repository.
