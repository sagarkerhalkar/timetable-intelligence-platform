## Root cause of backend test failure

The installer invoked pytest while current location was the repository root:

```powershell
Push-Location $Root
& $python -m pytest "services\api\tests" -q
```

The backend tests import `app.database`, which requires `services\api` to be on Python's import path / current working directory. The test command therefore used the wrong import context.

This is an **installer acceptance-gate defect**, not evidence that the v1.0.25 QR TypeScript payload itself failed.

Required correction for the next installer:

```powershell
$apiDir = Join-Path $Root "services\api"
Push-Location $apiDir
try {
  & $python -c "from app.database import Database; print('PASS backend import precheck')"
  & $python -m pytest "tests" -q
} finally { Pop-Location }
```

A fast backend import precheck must run before the full backend suite so a path/import mistake fails in seconds rather than wasting a long release cycle.

## Critical installer safety finding

Review of `INSTALL_V1_0_25_1.ps1` shows that its release backup covered:

- changed frontend source files;
- `apps\web\app\globals.css`;
- current `apps\web\.next` build.

It **did not back up the active SQLite database before applying/restarting**.

Also, this failed run stopped at backend import collection before the QR lifecycle probe ran. Therefore the installer did not reach its temporary QR create/delete acceptance probe.

Because the API was restarted after rollback, one plausible explanation for an empty QR library is that the restarted API resolved a different/new SQLite path rather than the previous populated DB. This must be verified read-only before any write/restore action. Do not assume deletion or corruption without locating all database files and counting `qr_codes` records.

## New mandatory database-safety release rule

Every future Windows release installer must, before changing source or stopping services:

1. Resolve the exact active production DB path used by the running API.
2. Record the DB path, size, modified time and SHA-256 in the release log.
3. Open it read-only and record counts for `qr_codes`, `qr_scans`, `qr_templates`, `sources` and other critical tables.
4. Copy the active DB plus SQLite WAL/SHM companions when applicable into the release backup using a safe SQLite-consistent backup method.
5. Never run destructive/migration tests against the production DB; test suites must use isolated temporary/test DBs.
6. After restart, verify that the API is using the same intended production DB path.
7. Verify post-start critical record counts against the pre-update snapshot.
8. If DB identity/count verification fails, stop acceptance and restore/rollback before declaring success.
9. Keep the database backup until explicit post-acceptance confirmation.
10. Port 3457 remains protected.
